# Аутентификация — серверные сессии с cookie

## Контекст и постановка задачи

Пользователь должен входить и выходить из системы (REQ-AUTH-003), доступ к долгам разграничивается (REQ-SEC-003), пароли хранятся хэшем (REQ-SEC-001), после пяти неудачных попыток вход блокируется на 15 минут (REQ-SEC-005). Клиент — same-origin SPA за одним доменом через nginx.

Вопрос: хранить ли состояние входа на сервере (сессия) или передавать самодостаточный токен (JWT) клиенту?

## Драйверы решения

* Немедленный отзыв доступа при выходе и блокировке — REQ-AUTH-003, REQ-ADM-001.
* Защита от XSS: cookie недоступна скриптам — REQ-SEC-004.
* Простота реализации и отладки.

## Рассмотренные варианты

* Серверные сессии с cookie HttpOnly, Secure, SameSite=Strict
* JWT в localStorage
* JWT в HttpOnly cookie

## Итог решения

Выбранный вариант: «Серверные сессии с cookie», потому что выход и блокировка мгновенно отзывают доступ (сессия удаляется на сервере), а cookie недоступна JavaScript. JWT в localStorage отклонён из-за риска кражи через XSS. JWT в cookie не даёт мгновенного отзыва без дополнительного списка отзыва, который фактически восстанавливает состояние на сервере.

### Последствия

* Хорошо, потому что блокировка пользователя (F-12) действует сразу.
* Хорошо, потому что Spring Security даёт сессии из коробки (ADR-0001).
* Плохо, потому что сервер хранит состояние; для нескольких экземпляров API нужна общая БД сессий (вне текущей версии, один экземпляр).
* Плохо, потому что CSRF-защиту нужно включить явно (токен для изменяющих запросов).

### Подтверждение

* Тест: после выхода старая cookie не даёт доступа к `/api/me`.
* Тест: cookie имеет флаги HttpOnly, Secure, SameSite=Strict.

## Плюсы и минусы вариантов

### Серверные сессии

* Хорошо, потому что мгновенный отзыв.
* Плохо, потому что состояние на сервере.

### JWT в localStorage

* Хорошо, потому что без состояния на сервере.
* Плохо, потому что доступен для скриптов, риск XSS-кражи.
* Плохо, потому что отзыв невозможен без списка отзыва.

### JWT в HttpOnly cookie

* Хорошо, потому что без состояния на сервере.
* Плохо, потому что отзыв требует списка отзыва, то есть состояния на сервере.

## Дополнительная информация

Связанные требования: REQ-AUTH-003, REQ-SEC-001, REQ-SEC-003, REQ-SEC-004, REQ-SEC-005, REQ-ADM-001. Связанные решения: ADR-0001, DES-003 (компонент безопасности).
