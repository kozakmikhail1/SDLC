## 1. Инженерия требований

### 1.1 IEEE 830-1998

**Название:** *IEEE Recommended Practice for Software Requirements Specifications*

**Историческое значение:** Это был *эталон* структуры SRS более 20 лет. Несмотря на то, что стандарт формально заменён на ISO/IEC/IEEE 29148, его структура до сих пор используется в большинстве корпоративных шаблонов и упоминается в академической литературе.

**Ключевые разделы по IEEE 830:**
1. Introduction (Purpose, Scope, Definitions, References, Overview)
2. Overall Description (Product Perspective, Functions, User Characteristics, Constraints, Assumptions)
3. Specific Requirements (External Interfaces, Functions, Performance, Logical Data, Quality Attributes)

**Когда использовать:** В legacy-проектах, где стандарт закреплён договором; в учебных курсах для понимания эволюции стандартов.

### 1.2 ISO/IEC/IEEE 29148:2018

**Название:** *Systems and software engineering — Life cycle processes — Requirements engineering*

**Текущий основной стандарт** инженерии требований. Разработан совместно ISO, IEC и IEEE, объединяет лучшие практики трёх организаций.

**Ключевые нововведения относительно IEEE 830:**
- Введение понятия **Requirement Information Item** — стандартизированной структуры требования с атрибутами (ID, источник, приоритет, статус, версия, связи).
- Явное разделение на **бизнес-требования**, **пользовательские требования** и **системные требования**.
- Усиление акцента на **трассируемости** и **управлении изменениями**.
- Поддержка **итеративных методологий** (Agile).

**Процессы, описанные в стандарте:**
- Business requirements definition
- Stakeholder requirements definition
- System requirements analysis
- Requirements specification
- Requirements verification & validation
- Requirements management

### 1.3 ISO/IEC/IEEE 12207:2017

**Название:** *Systems and software engineering — Software life cycle processes*

Описывает полный набор процессов жизненного цикла ПО. Важные для документации процессы:
- **Agreement processes** — договорные процессы (требования к SRS как артефакту поставки).
- **Technical management processes** — управление конфигурацией, рисками, качеством.
- **Technical processes** — требования, архитектура, реализация, интеграция, верификация.

### 1.4 ISO/IEC/IEEE 15289:2019

**Название:** *Systems and software engineering — Content of life-cycle information items*

Определяет **содержимое** информационных элементов ЖЦ, включая:
- Software Requirements Specification (SRS)
- Software Design Description (SDD)
- Architecture Description
- Test Plans и Test Reports

Стандарт работает в паре с 12207: 12207 описывает *процессы*, 15289 — *артефакты* этих процессов.

## 2. Архитектура и дизайн

### 2.1 IEEE 1016-2009 (SDD)

**Название:** *Systems and software engineering — Software design description*

**Важное замечание о терминологии:**
- В версии 1998 года стандарт назывался *Software Design Specification* (SDS).
- В версии 2009 года переименован в *Software Design Description* (**SDD**).

Термин **SDD** сегодня является актуальным в международной инженерной практике. Устаревший термин **SDS** всё ещё встречается в старых проектах и учебной литературе.

**Ключевая концепция:** SDD описывает *как* система будет построена, в отличие от SRS, описывающего *что* система должна делать.

**Основные разделы по IEEE 1016:**
1. Design Overview
2. Design Viewpoints (точки зрения)
3. Design Views (представления — экземпляры точек зрения)
4. Design Decisions

### 2.2 ISO/IEC/IEEE 42010:2011 (Архитектура)

**Название:** *Systems and software engineering — Architecture description*

Фундаментальный стандарт для описания архитектуры. Вводит три ключевых понятия:

| Понятие | Определение | Пример |
|---------|-------------|--------|
| **Stakeholder** | Лицо, система или организация, заинтересованные в системе | Заказчик, оператор, регулятор |
| **Concern** | Заинтересованность стейкхолдера в системе | Производительность, безопасность |
| **Viewpoint** | Конвенция о построении и использовании View | Deployment Viewpoint |
| **View** | Представление архитектуры с точки зрения одного Viewpoint | Диаграмма развёртывания AWS |

**Соотношение 42010 и IEEE 1016:**
42010 задаёт концептуальную рамку (что такое архитектура), 1016 конкретизирует её для ПО (какие разделы должен содержать SDD).

### 2.3 Модель «4+1 представлений» (Крухтен)

Хотя формально не является стандартом, архитектурная модель Филиппа Крухтена (1995) де-факто стала основой для 42010 и IEEE 1016.

| Представление | Адресует | UML-диаграммы |
|--------------|---------|---------------|
| **Logical View** | Функциональность для конечного пользователя | Class, State, Activity |
| **Development View** | Организация кода для разработчика | Component, Package |
| **Process View** | Параллелизм, производительность | Sequence, Activity |
| **Physical View** | Развёртывание для инженера эксплуатации | Deployment |
| **Use Case View** (+1) | Сценарии, связывающие все представления | Use Case |

## 3. Качество ПО

### 3.1 ISO/IEC 25010:2011 (SQuaRE)

**Название:** *Systems and software Quality Requirements and Evaluation (SQuaRE) — System and software quality models*

Стандарт определяет **модель качества ПО** с 8 основными характеристиками и их подхарактеристиками:

1. **Functional suitability** — функциональная пригодность
   - completeness, correctness, appropriateness
2. **Performance efficiency** — производительность
   - time behaviour, resource utilisation, capacity
3. **Compatibility** — совместимость
   - co-existence, interoperability
4. **Usability** — удобство использования
   - learnability, operability, user error protection, aesthetics, accessibility
5. **Reliability** — надёжность
   - maturity, availability, fault tolerance, recoverability
6. **Security** — безопасность
   - confidentiality, integrity, non-repudiation, authenticity, accountability
7. **Maintainability** — сопровождаемость
   - modularity, reusability, analysability, modifiability, testability
8. **Portability** — переносимость
   - adaptability, installability, replaceability

**Использование в SRS:** Атрибуты качества из ISO 25010 — это основа раздела *Non-functional Requirements* / *Quality of Service*.

## 4. Национальные стандарты (СНГ)

### 4.1 ГОСТ 34.602-89 / ГОСТ 34.602-2020

**Название:** *Техническое задание на создание автоматизированной системы*

**ГОСТ 34.602-89** — классический стандарт для госсектора СНГ. Используется в Waterfall-проектах с государственной приёмкой.

**ГОСТ 34.602-2020** — обновлённая версия, вступившая в силу 1 января 2022 года, заменяющая ГОСТ 34.602-89. Учитывает:
- Электронный документооборот с ЭЦП
- Итеративные методологии
- Расширенный состав разделов ТЗ

**Структура ТЗ по ГОСТ 34.602:**
1. Общие сведения
2. Назначение и цели создания системы
3. Характеристика объектов автоматизации
4. Требования к системе
5. Состав и содержание работ
6. Порядок контроля и приёмки
7. Требования к документированию
8. Источники разработки

### 4.2 ГОСТ 19.201-78 (ЕСПД)

**Название:** *Техническое задание. Требования к содержанию и оформлению*

Часть **Единой системы программной документации** (ЕСПД). Применяется для «коробочного» ПО. Более формальный, но менее гибкий, чем ГОСТ 34.

## 5. Отраслевые стандарты

### 5.1 IEC 62304 — Медицинские изделия

Определяет жизненный цикл ПО медицинских изделий. Вводит **классы безопасности**:
- **Class A** — не может привести к травме
- **Class B** — может привести к незначительной травме
- **Class C** — может привести к смерти или серьёзной травме

Требования к документации возрастают от класса A к классу C.

### 5.2 DO-178C — Авионика

**Название:** *Software Considerations in Airborne Systems and Equipment Certification*

Требует **полной трассируемости** от требований до строки кода (уровень детализации — максимальный). Применяется в гражданской авиации.

### 5.3 ISO 26262 — Автопром

**Название:** *Road vehicles — Functional safety*

Вводит понятие **ASIL** (Automotive Safety Integrity Level, A–D). Требования к трассируемости safety-требований возрастают с уровнем ASIL.

### 5.4 PCI DSS — Финансы

**Название:** *Payment Card Industry Data Security Standard*

Требует трассируемости требований безопасности и регулярного аудита.
